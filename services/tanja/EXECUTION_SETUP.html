TANJA · STEP 3A · CONNECTION TEST

Verify delivery, then verify the actual trade.

Your 50K Builder account is already connected to Tradovate in TradersPost. You want to verify a real entry and exit. There are two distinct checks below.

CheckWhat it verifiesAvailable now
Railway → TradersPost test signalThe private webhook receives the request. No broker order.This update adds a dashboard button and saved receipts.
TradersPost → Builder position → exitAccount routing, actual fill, protective orders and closure.User submits/approves the chosen trade after checking account conditions. This service does not send non-test orders or import fills.

The service remains OBSERVE_ONLY, with orders_enabled: false. Its only outgoing TradersPost message has test: true fixed in code. This is not yet autonomous Tanja execution, nor a full live test of the AI strategy.

1. Create a separate Tanja strategy in TradersPost

  1. Open Strategies and create Tanja — Builder 50K with asset class Futures.
  2. Keep Allow Auto Submit disabled. On the account subscription, keep Auto Submit disabled too.
  3. Select your existing Tradovate connection and the exact Builder account for this subscription. Check the account identifier yourself. Do not attach extra accounts.
  4. For the eventual small trade test, set fixed size to one MNQ contract, quantity multiplier 1, and disable adding to an existing position. Verify these settings on the subscription, since strategy defaults can differ.
  5. Copy this new strategy's private webhook URL. Do not reuse the Agent 50k strategy webhook. Keep the URL out of chat, screenshots, GitHub and Pine.

Separate strategy names do not isolate positions held on the same brokerage account. Before the actual trade test, check whether Agent 50k or another process is managing the same account/instrument. Do not let independent exit logic act on the test position.

2. Upload the update

  1. Unzip Tanja_Railway_Step3_ConnectionTest_20261008.zip.
  2. Update services/tanja/ in your existing GitHub repository from the extracted folder. Preserve that path and the current Railway root directory.
  3. Keep the existing /data volume, feed variables, dashboard password and AI variables. The update only adds a connection-test table to the database.
  4. Deploy to your existing tanja service. /health should show version: "2.1-test-only" and orders_enabled: false.

3. Set two Railway variables

NameValue
TANJA_TRADERSPOST_TEST_WEBHOOK_URLPaste the private URL of the new Tanja strategy directly into Railway.
TANJA_TEST_CONTRACTThe exact MNQ contract, in TradersPost format. For example MNQZ2026 means December 2026; confirm the contract you intend to use in Tradovate. This example is not an automatic contract selection.

Apply and deploy. Do not change TANJA_MNQ_TICKER: that controls the existing data feed. There is no live-orders enable flag in this build.

4. Run the connection test now

  1. Open Tanja → 50K Builder executions. Check the displayed contract and Ready for connection test.
  2. Click Send test signal — no broker order once.
  3. Look for test_received and a TradersPost signal ID in the history.
  4. Open that signal in TradersPost and confirm it belongs to the new Tanja strategy and is marked as a test. Check the intended account subscription there.
  5. In Tradovate, verify that no new position or working order was created. That is the expected outcome of this check.

The request is a fixed one-MNQ buy-shaped test message, not a trading recommendation. It uses real HTTP delivery, expires after 60 seconds, and cannot place an order according to TradersPost's documented test-mode behavior. It does not call OpenAI or wait for AI warmup.

Five tests per rolling 24 hours and a 60-second gap prevent repeated clicks from flooding the webhook. The same request ID is never resent. Network/interruption outcomes are marked unknown; inspect the TradersPost log before trying again. The webhook secret is never displayed or stored in test history.

If delivery is rejected, check the webhook URL, strategy settings and source-IP restrictions. The request comes from Railway, so a TradingView-only IP restriction will not match. Use an appropriate allowlist for your Railway egress setup if configured; do not change unrelated strategy restrictions.

5. Prepare the actual Builder entry/exit test

Before the actual order: pause the Agent 50k subscription's order delivery to this account in TradersPost. Confirm it is disabled, the account is still flat, and no orders remain. Keep it paused until the test position is closed and test bracket orders are gone. The no-order test in step 4 does not require interrupting Agent 50k.

This step changes your Builder account and can incur P&L and fees. Before choosing the actual order, record:

  • Evaluation, sim-funded or live stage; default Builder or Add-On loss-limit option.
  • Current balance/equity, current minimum balance / maximum-loss threshold, and remaining daily loss allowance if applicable.
  • Current positions and working orders; whether Agent 50k or another strategy is trading this exact account.
  • The exact contract, your selected direction, entry order/price, protective stop, take-profit and acceptable test loss.

The nominal “50K” name does not establish available risk. The current account dashboard and remaining cushion matter. This service cannot query those values through a signal webhook.

Once these are verified, you can prepare the trade in TradersPost's own order/signal interface (or Command Pad), review its complete payload and manually approve it. I can help check the configuration and records; I cannot submit or close the trade on your behalf. Keep automatic submission disabled for this test.

6. Actual trade acceptance record

For the trade you submit, check and record the following:

  1. The intended Builder account and exact contract, with the intended quantity.
  2. A broker order ID and actual entry fill. An HTTP success or TradersPost receipt alone is insufficient.
  3. Accepted protective stop and target orders at the intended prices and quantities. A drawn chart box is insufficient.
  4. Your submitted exit and its actual fill, or the bracket exit's fill.
  5. The account is flat for the test instrument and there are no remaining test bracket orders.
  6. Realized P&L, fees, and entry/exit timestamps from broker records.

If execution or protective orders differ from the intended plan, use the broker's own controls to manage the position rather than repeatedly sending uncertain webhook requests. An open position cannot be assumed closed from a dashboard message.

What remains for automated Tanja trading?

The first real AI response still needs validation, then forward observation on unseen sessions. The current code has no approved AI-to-order bridge, account-wide risk synchronization, broker position reconciliation or verified fill import. Those must be built and checked before automated entries. Passing a connectivity test or one manual trade does not establish strategy fidelity or profitability.
