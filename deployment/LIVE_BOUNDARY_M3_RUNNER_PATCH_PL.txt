CYKL POZYCJI
- Dopiero wynik SENT (zaakceptowana emisja entry z prawidłową ilością) tworzy ASSUMED_OPEN.
- Cena assumed to cena LIMIT, czas assumed to czas zaakceptowania emisji. To założenie, nie broker fill.
- Nie czeka na POSITION ani FLAT. Nie czeka na dotknięcie LIMIT i nie wygasa automatycznie po 10 minutach.
- NO_FILL / CANCELLED / EXPIRED z poprawnym order_id usuwa position_json, blokuje późniejsze callbacki,
  inference i dispatch. Wiersz order pozostaje jako terminalny zapis chroniący przed odtworzeniem trade'u.
  Historyczne score'y i decyzje pozostają do audytu, ale nie są wykonywalne.
- POSITION z prawidłową własnością/ilością/geometrią promuje do BROKER_CONFIRMED_OPEN; częściowe fills
  lub rozbieżności nadal trafiają do OWNERSHIP_MISMATCH. Żaden obcy trade nie jest adoptowany.
- CLOSED po zaakceptowanym wyjściu assumed, dotknięciu SL/targetu w danych 1s lub zaakceptowanym
  Guard flatten ma closure_basis=ASSUMED_*. Nie wpisuje ceny rzeczywistego fill ani broker P&L.
- Po promocji na potwierdzoną pozycję final CLOSED wymaga zdarzenia CLOSED brokera.
- Niepewny wynik HTTP wyjścia pozostaje EXIT_UNKNOWN, bez automatycznej ponownej emisji.
- SQLite serializuje anulowanie z ostatnią kontrolą przed wysłaniem exit. Polecenia już wysłanego nie da
  się cofnąć; anulowanie zaakceptowane przed jego emisją uniemożliwia wysłanie.
- Guard przejmuje pozycję przed flatten; recovery nie blokuje Guard/SL. Orphan sweep nie traktuje
  modelowanego no_fill ze starego shadow book jako jawnego NO_FILL aktywnej assumed position.

BOUNDARY I MANAGER
Niezmienione artefakty: WIN_TEMPORAL_CHECK (WinExpert), CHRONO_94_24 (LossExpert), BOUNDARY_MODEL.
Hash każdego jest sprawdzany przy ładowaniu; żadnego fit/retrain. Brak lub uszkodzony model blokuje nowe entry LIVE.
WIN >=0.50 i LOSS >=0.75 w tej samej minucie uruchamia frozen Boundary.
Frozen Boundary: RECOVERY gdy score>=0.70 i bootstrap p10>0.50;
FAILURE gdy score<=0.30 i bootstrap p90<0.50; inaczej AMBIGUOUS.
Poza HIGH-HIGH: NO_BOUNDARY_YET. To score'y frozen, nie nowe skalibrowane prawdopodobieństwa.

FAILURE -> LOSER_LIKELY, CLOSE tylko z potwierdzonym M3.
RECOVERY -> WINNER_LIKE / RECOVERY, blokuje M3 (zgodnie z ustaleniem).
AMBIGUOUS / NO_BOUNDARY_YET -> standardowe validated M3.
M3: F2, B11, OBFH_EXPANSION, OBFH_3_CLOSES_10M; kolejność i formuły bez zmian w v3_frozen_exit.py.
B13/MSS oraz S1-S4/retest A/B są wejściowymi obserwacjami frozen ekspertów, NIE dodatkowymi close rules.
Nowe pozycje nie przechodzą przez równoległe stare M1/M2/MTF managery. Stare pozycje OPEN zachowują
wcześniejszą ścieżkę; patch nie migruje ani nie adoptuje otwartych pozycji sprzed wdrożenia.

RUNNER I CZAS WYKONANIA
Niezmienione v3_runner.py / v3_runner_model_2026.json; probability >0.75 -> HOLD_3R, <=0.75 -> EXIT_2R.
SL i docelowy bracket 3R pozostają oryginalne; runner jest podejmowany raz, przy pierwszym dostępnym 2R.
Po 2R M3 nie generuje późniejszych failure exits. Boundary może dalej zapisywać obserwacje.
Brak pełnych wejść modelu/sekund dotknięcia -> zachowany konserwatywny EXIT_2R_DATA_FALLBACK.
Model 0 nie obsługuje dotknięcia 2R w minucie fill: ten przypadek również używa fallback, bez zmiany modelu.
Zachowana ważność zamrożonego Model 0 na rok 2026.

Feed TV wysyła zamknięte paczki minutowe. Timestamp dotknięcia i timestamp emisji są rozdzielone:
wyjście jest rynkowe po otrzymaniu danych, a NIE gwarantowanym wykonaniem po historycznej cenie 2R.
Runner akceptuje świeżą paczkę zawierającą touch sprzed <=75 s oraz M1 zamknięty <=15 s temu;
przed HTTP nadal obowiązuje świeżość 1s <=5 s i sygnału <=10 s. M3 nie wykonuje historycznych zaległych sygnałów.
Zaobserwowane SL/3R w paczce mają pierwszeństwo przed nową próbą close.
