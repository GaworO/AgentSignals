# AgentSignals v32.0 deployment

## What v32 changes

v32.0 makes the execution path internally consistent:

1. `ExecutionPlan` is the canonical entry/SL/TP/quantity/TIF contract.
2. `entry_ms` is the first **theoretically legal** time for a resting order.
3. The live effective order time becomes `max(entry_ms, broker_accepted_ms)`.
4. The guard can receive authenticated broker lifecycle callbacks and uses broker truth before shadow results.
5. All strategy/session labels use one fixed `UTC-04:00` clock.
6. UTC epoch milliseconds remain the canonical stored timestamp.
7. The status endpoint reports `v32.0-execplan-broker-sync`.

## Important clock warning

This project now follows the operator-requested **fixed UTC-04:00 strategy clock**. It does not change for daylight-saving time.

Therefore:

- in summer, fixed UTC-04:00 matches New York EDT;
- in winter, fixed UTC-04:00 is one hour ahead of New York EST;
- the detector, guard, shadow and satellite strategies still agree with one another;
- `cme_calendar.py` intentionally remains on `America/Chicago`, because exchange holidays and maintenance hours must be evaluated in the exchange clock.

Do not replace `timebase.STRATEGY_TZ` with the server's local timezone.

## `entry_ms` in plain language

For a one-minute setup:

- `bos_ms` is the timestamp of the signal/BOS bar;
- the setup is not known until that bar has closed;
- `entry_ms` is normally the next one-minute timestamp;
- the order may fill on the bar beginning at `entry_ms`;
- it may never fill on the earlier signal bar.

`entry_ms` does **not** change the entry price, SL, TP, setup class or strategy edge. It only prevents look-ahead and impossible same-bar fills.

In live trading the webhook and broker introduce latency. v32 therefore records:

```text
broker_active_from_ms = max(entry_ms, broker_accepted_ms)
```

The broker's accepted time is authoritative when available.

## Environment variables

Required for broker feedback:

```text
GUARD_TOKEN=<strong-secret>
BROKER_EVENT_TOKEN=<strong-separate-secret>   # optional; falls back to GUARD_TOKEN
BROKER_FEEDBACK_REQUIRED=1
BROKER_ACK_MAX_SEC=30
```

Execution defaults:

```text
BUFFER_BARS=14000
EXEC_TICK=0.25
EXEC_FILL_THROUGH_TICKS=1
EXEC_FILLBAR_TP=0
EXEC_ADVERSE_FIRST=1
EXEC_TIF=day
FILL_WIN_MIN=10
PARTIAL_AT_1R=0
RAMP_TRADES=10
```

Current selective auto-session policy:

```text
SKIP_SESSIONS=LO,ASIA,PREM,NYL
```

This means PREM and ASIA are detected and can be logged in shadow, but are not sent by the main Auto-Executor.

## Broker callback endpoint

The relay must POST broker lifecycle events to:

```text
POST https://<agent-host>/guard/broker-event?t=<BROKER_EVENT_TOKEN>
Content-Type: application/json
```

Recommended normalized payload:

```json
{
  "plan_id": "0f91...",
  "signal_key": "A/B|LONG|...",
  "order_id": "broker-123",
  "status": "accepted",
  "event_ms": 1785432000123,
  "ticker": "MNQ1!",
  "side": "LONG",
  "quantity": 4
}
```

Fill update:

```json
{
  "plan_id": "0f91...",
  "order_id": "broker-123",
  "status": "filled",
  "event_ms": 1785432015000,
  "filled_quantity": 4,
  "avg_fill_price": 30125.25
}
```

Close update:

```json
{
  "plan_id": "0f91...",
  "order_id": "broker-123",
  "status": "closed",
  "event_ms": 1785432315000,
  "exit_price": 30175.25,
  "realized_pnl": 397.76
}
```

Accepted statuses are normalized to:

```text
submitted, accepted, working, partial, filled,
closed, canceled, rejected, expired
```

The order text generated by v32 includes:

```text
[plan:<plan_id>] [signal:<signal_key>] [leg:<n>/<total>]
```

The relay should preserve or parse these values and echo them in callbacks.

## Guard behavior with broker feedback

The guard treats these as live commitments:

```text
submitted, accepted, working, partial, filled
```

The one-position slot is released only by:

```text
closed, canceled, rejected, expired
```

When `realized_pnl` arrives, broker P&L becomes authoritative for:

- daily net P&L;
- loss count;
- profit lock;
- drawdown logic;
- the guard table's “Real$ (broker)” column.

If the relay accepts an order but no broker callback arrives within `BROKER_ACK_MAX_SEC`, `/guard/health` becomes critical when `BROKER_FEEDBACK_REQUIRED=1`.

## Deployment order

1. Back up the persistent volume: `guard_log.json`, `guard_state.json`, `shadow_log.json`, `archive.csv`.
2. Deploy v32 with `AUTO_SUBMIT=0` and guard mode `manual`.
3. Set `GUARD_TOKEN` and `BROKER_EVENT_TOKEN`.
4. Configure the relay callback to `/guard/broker-event`.
5. Send one test order and verify status progression in `/guard`:
   `relay accepted → broker accepted/working → filled → closed/canceled`.
6. Verify `/guard/health` has no `broker_feedback` critical error.
7. Keep `RAMP_TRADES=10` for the first accepted live orders.
8. Only then switch the guard mode to `auto`.
